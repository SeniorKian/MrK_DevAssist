# 36 — برنامه جامع موتور DNS حرفه‌ای MRK (MRK DNS)

وضعیت: **برنامه — 2026-11-08، منتظر تأیید مالک**. جایگزین بخش‌های «زبان/runtime» و «بودجه منابع» در `docs/23`
و §10 در `docs/25` می‌شود؛ رفتار و قابلیت‌ها همچنان از `docs/25` (مطالعه رفتاری Technitium + RFCها) و `docs/22` گرفته
می‌شود.

خواسته مالک: یک سرور DNS کاملاً حرفه‌ای در سطح Technitium و موتورهای سرورهای بزرگ (PowerDNS، Knot، Unbound، BIND)؛
امنیت، سادگی کاربری و امکانات «۱۰ از ۱۰»؛ زیر بار سنگین سرور اصلی از کار نیفتد؛ ایمیج جداگانه نداشته باشیم ولی
قدرتمند باشد؛ مدیریت لاگ DNS بسیار قوی؛ پایش بحرانی و کنترل خودکار مصرف؛ «دور زدن تحریم» با دو کلیک.

## 1. تصمیم‌های پایه (تغییر نسبت به docs/23)

| موضوع | قبلی | جدید و دلیل |
|---|---|---|
| زبان موتور | Python asyncio (هدف ۵ هزار qps) | **Go** (باینری استاتیک، بدون runtime، چند هسته‌ای واقعی؛ هدف ≥ ۱۰۰ هزار qps از cache روی ۲ هسته). کتابخانه پروتکل: `github.com/miekg/dns` (BSD-3؛ همان کتابخانه‌ای که CoreDNS روی آن ساخته شده) — کتابخانه است نه محصول؛ منطق سرور، resolver، cache، سیاست‌ها، لاگ و API همه کد خود MRK. |
| ایمیج | یک ایمیج | **همچنان یک ایمیج**؛ باینری `mrk-dns` و `mrk-sniproxy` (Go) در همان ایمیج قرار می‌گیرند (حدود ۲۰ مگابایت اضافه). |
| اجرا | process داخل همان container | **یک container جدا از همان ایمیج** (`mrk-dns` در compose با `command` متفاوت). دلیل: محدودیت CPU/RAM/PIDs مستقل با cgroup؛ اگر DNS زیر حمله باشد پنل، npm، PyPI و خود سرور سالم می‌مانند؛ اگر پنل ری‌استارت شود DNS قطع نمی‌شود. |
| ذخیره | PGlite مشترک | پیکربندی و زون‌ها: فایل‌های اتمیک نسخه‌دار در volume خود DNS (موتور بدون پنل هم کار می‌کند)؛ پنل مرجع ویرایش است و از API مدیریتی موتور اعمال می‌کند. لاگ‌ها: ذخیره‌ساز اختصاصی (بخش 5)، هرگز در PGlite. |

## 2. معماری اجرا و ایزوله‌سازی

```
                 ┌──────────── mrk-dns container (same image) ────────────┐
client ──53/udp,tcp──▶ listeners ─▶ guard (ACL, RRL, cookies, sanity) ─▶ policy (views, block, bypass)
       ──853 DoT / DoH / DoQ──▶        └▶ authoritative zones │ cache │ recursive / forwarders
                 │  log ring buffer ─▶ log writer (segments+index) ─▶ stats aggregator
                 │  admin API (unix socket + token) ◀── control-plane module "dns"
                 └─ mrk-sniproxy (same container, separate process) for bypass ─┘
```

- **شبکه:** پیش‌فرض `network_mode: host` با `CAP_NET_BIND_SERVICE` فقط، bind روی نشانی‌هایی که کاربر انتخاب می‌کند
  (پیش‌فرض: `127.0.0.1` و gateway شبکه‌های Docker مثل `172.17.0.1`). دلیل: docker-proxy برای UDP زیر بار کند است و IP واقعی
  کلاینت را از دست می‌دهد. پاسخ‌دادن به اینترنت (authoritative عمومی) فقط با انتخاب صریح؛ recursion برای بیرون هرگز.
- **محدودیت منابع (قابل تنظیم):** پیش‌فرض `cpus: 2`، `mem_limit: 512m`، `pids_limit: 256`؛ موتور خودش سقف حافظه
  (`GOMEMLIMIT`)، سقف cache، سقف اتصال TCP/DoT همزمان و صف محدود دارد و هرگز بیش از سقف مصرف نمی‌کند.
- **سخت‌سازی container:** کاربر غیر root، `cap_drop: ALL` + `NET_BIND_SERVICE`، `read_only` rootfs، `no-new-privileges`،
  seccomp پیش‌فرض، فقط volume خودش.
- **وابستگی:** DNS به پنل وابسته نیست. اگر DNS بیفتد: docker restart policy + healthcheck داخلی؛ راهنمای راه‌اندازی
  همیشه یک DNS پشتیبان بیرونی کنار MRK قرار می‌دهد تا اینترنت سرور قطع نشود.

## 3. امکانات موتور (مرجع رفتار: docs/25)

**Authoritative:** زون Primary، Secondary (AXFR/IXFR + NOTIFY)، Stub، Forwarder (conditional forwarding)، Catalog؛
همه رکوردهای رایج (A، AAAA، CNAME، MX، TXT، SRV، NS، PTR، CAA، TLSA، SSHFP، NAPTR، SVCB/HTTPS، DS، URI و ...)،
ALIAS/ANAME (flatten در apex)، wildcard، رکوردهای PTR خودکار، import/export فایل زون RFC 1035، تاریخچه نسخه هر زون
و برگشت (rollback)، Dynamic Update (RFC 2136) با TSIG، Views/Split-horizon بر اساس شبکه مبدأ.

**DNSSEC:** اعتبارسنجی کامل در resolver (RFC 4033–4035، 5155، 6840، trust anchor ریشه + RFC 5011)؛ امضای آنلاین زون‌ها
با ECDSA P-256 و Ed25519، NSEC/NSEC3، چرخش خودکار کلیدها و راهنمای ثبت DS در registrar.

**Resolver:** حل کامل از ریشه (iterative) یا فقط forwarder یا ترکیبی؛ QNAME minimisation، 0x20، aggressive NSEC،
serve-stale (RFC 8767)، prefetch رکوردهای پرمصرف، cache با سقف حافظه و LRU؛ forwarderهای UDP/DoT/DoH/DoQ با
health-check، انتخاب سریع‌ترین، موازی؛ ECS اختیاری؛ DNS cookies.

**پروتکل‌ها (ورودی):** UDP/TCP 53، DoT 853، DoH (HTTP/2 و HTTP/3)، DoQ؛ PROXY protocol برای پشت proxy؛ گواهی از
Let's Encrypt (یا دستی).

**فیلترینگ:** فهرست‌های مسدودسازی (تبلیغات/بدافزار) با به‌روزرسانی خودکار، allowlist، RPZ، گروه‌های کلاینت با
سیاست جدا، پاسخ مسدود قابل انتخاب (NXDOMAIN، 0.0.0.0، صفحه مسدود)، محافظت DNS rebinding.

**امنیت (۱۰ از ۱۰):** هرگز open resolver نیست (recursion فقط برای شبکه‌های مجاز)؛ Response Rate Limiting و سقف qps
به ازای هر کلاینت/زیرشبکه؛ محافظت amplification (حداکثر اندازه UDP 1232، TC برای ANY)؛ بررسی سلامت بسته؛ TSIG برای
انتقال و update؛ ACL انتقال زون؛ API مدیریتی فقط روی unix socket با توکن و امضا؛ fuzzing پارسر و سیاست‌ها در CI؛
audit همه تغییرات در پنل؛ پشتیبان‌گیری رمزنگاری‌شده همراه با پشتیبان پنل.

**یکپارچگی با MRK:** دامنه‌هایی که در «سرویس‌های من» اضافه می‌شوند خودکار در زون داخلی رکورد می‌گیرند؛ رکورد
`*.mrk.internal` برای سرویس‌ها؛ هشدارها از مرکز اعلان (تلگرام/بله/ایمیل).

## 4. پایش بحرانی و مدیریت خودکار بار

- **سنجه‌ها (هر ثانیه):** qps کل و به ازای کلاینت/دامنه، نرخ cache hit، تأخیر p50/p95/p99، SERVFAIL/NXDOMAIN، صف‌ها،
  حافظه، CPU container، اتصال‌های TCP، وضعیت forwarderها؛ مصرف کل سرور از Host Agent.
- **سطوح فشار:** عادی ← هشدار ← بحرانی ← اضطراری (آستانه‌ها قابل تنظیم). در هر سطح، اقدام‌های خودکار و قابل برگشت:
  - نمونه‌برداری لاگ (۱۰۰٪ ← ۱۰٪ ← فقط خطاها) به جای از دست دادن DNS؛
  - خاموش کردن prefetch و حل از ریشه، تکیه بیشتر به cache و serve-stale؛
  - سخت‌تر شدن سقف qps کلاینت‌های پرمصرف؛
  - شناسایی «دامنه‌ها و کلاینت‌های داغ» (top-k بلادرنگ با Count-Min Sketch) و: cache اجباری، کند کردن، یا مسدودسازی
    موقت با تأیید یا خودکار (قابل انتخاب)؛
  - تشخیص الگوهای حمله: random-subdomain (water torture)، NXDOMAIN flood، amplification؛
  - در نهایت پاسخ REFUSED به کلاینت‌های غیرمجاز قبل از رسیدن به سقف container.
- **پنل:** صفحه «وضعیت زنده» با نمودار لحظه‌ای، فهرست داغ‌ترین دامنه‌ها/کلاینت‌ها با دکمه «کند کن / مسدود کن / آزاد کن»،
  تاریخچه رخدادهای فشار و اقدام‌های خودکار انجام‌شده؛ اعلان فوری.

## 5. مدیریت لاگ DNS

- **مسیر داغ هرگز منتظر لاگ نمی‌ماند:** هر پاسخ یک رکورد فشرده در ring buffer بدون قفل؛ اگر پر شد، شمارش «لاگ‌های
  ازدست‌رفته» و نمونه‌برداری خودکار، نه کند شدن DNS.
- **ذخیره:** segmentهای ستونی فشرده (zstd) به ازای هر دقیقه با index زمان/کلاینت/دامنه/نوع/rcode و Bloom filter؛
  جست‌وجو روی میلیون‌ها رکورد در کسری از ثانیه بدون دیتابیس جدا.
- **نگهداری:** بر اساس زمان و حجم (مثلاً ۷ روز یا ۵ گیگابایت، هر کدام زودتر)؛ آمار تجمیعی دقیقه/ساعت/روز جدا و طولانی‌تر
  (مثلاً ۱ سال)؛ هرگز دیسک را پر نمی‌کند (توقف خودکار ذخیره کامل در کمبود دیسک).
- **پنل:** جست‌وجو و فیلتر (دامنه، کلاینت، نوع، نتیجه، مسدود/بای‌پس شده، بازه زمانی)، نمایش زنده (tail)، گروه‌بندی،
  خروجی CSV/NDJSON، حذف لاگ یک کلاینت، حالت حریم خصوصی (ناشناس‌سازی IP کلاینت قابل انتخاب)، ارسال اختیاری به
  syslog/HTTP بیرونی.

## 6. دور زدن تحریم (Smart DNS + SNI Proxy) — دو کلیک

**تجربه کاربر:** «دور زدن تحریم» ← روشن ← انتخاب سرویس‌ها از کارت‌های آماده (Docker Hub، npm، PyPI، GitHub، Google،
Go modules، Maven، Hugging Face، OpenAI/Anthropic API، ...) یا افزودن دامنه دلخواه ← انتخاب پروکسی از پروفایل‌های
موجود (SOCKS5/HTTP/سرور خارجی) ← تمام. یک دکمه «امتحان کن» نشان می‌دهد هر سرویس الان باز است یا نه.

**سازوکار (قوی):**
1. DNS برای دامنه‌های انتخاب‌شده به جای IP واقعی، نشانی SNI Proxy خود MRK را برمی‌گرداند (بر اساس view: برای خود
   سرور، containerها یا شبکه داخلی نشانی مناسب).
2. `mrk-sniproxy` روی 443/80 آن نشانی، SNI/Host را می‌خواند (بدون باز کردن رمز TLS)، فقط اگر دامنه در فهرست مجاز باشد،
   اتصال را از طریق پروکسی انتخاب‌شده به مقصد واقعی می‌برد. فهرست مجاز اجباری است تا پروکسی باز نشود.
3. نام واقعی مقصد از طریق DoH روی همان پروکسی حل می‌شود (جلوگیری از پاسخ‌های مسموم داخلی).
4. چند پروکسی با health-check و جابه‌جایی خودکار؛ قانون به ازای هر دامنه (این پروکسی/آن پروکسی/مستقیم).
5. هم‌زیستی با Dokploy: چون Traefik پورت 443 عمومی را دارد، برای کلاینت‌های بیرون از سرور، مسیر TCP با `HostSNI`
   (passthrough، بدون باز کردن TLS) در فایل Traefik مخصوص MRK اضافه می‌شود؛ برای خود سرور و containerها SNI Proxy روی
   یک نشانی داخلی اختصاصی گوش می‌دهد. جزئیات و آزمون روی Docker واقعی در فاز مربوط بررسی و مستند می‌شود.
6. Docker daemon، npm، pip و ... بدون هیچ تنظیم جدا از همین DNS استفاده می‌کنند.

## 7. راه‌اندازی روی سرور (راهنمای قدم‌به‌قدم در پنل با بررسی خودکار)

1. **آزاد کردن پورت 53:** تشخیص اشغال‌کننده (اغلب `systemd-resolved`) و دستور دقیق (`DNSStubListener=no`) با کپی.
2. **روشن کردن container DNS** با پروفایل compose (`docker compose --profile dns up -d`).
3. **DNS خود سرور:** تنظیم `resolved.conf`/`resolv.conf` به MRK + یک DNS پشتیبان.
4. **Docker daemon:** `/etc/docker/daemon.json` → `"dns": ["172.17.0.1", "<پشتیبان>"]` (نه 127.0.0.1، چون containerها
   آن را نمی‌بینند)؛ هشدار صریح که ری‌استارت Docker روی سرویس‌های Dokploy اثر دارد و بهتر است در زمان خلوت باشد.
5. **بررسی نهایی:** پنل از خود سرور و از یک container پرس‌وجوی آزمایشی می‌فرستد و نتیجه را نشان می‌دهد.
MRK خودش فایل‌های سیستمی را تغییر نمی‌دهد (امنیت)؛ دستور دقیق می‌دهد و بعد بررسی می‌کند. هر قدم برگشت‌پذیر و دکمه
«برگرداندن» دارد.

## 8. پنل

- **ساده:** وضعیت DNS (یک جمله)، «دامنه‌های من» با افزودن/حذف رکورد به زبان ساده («این نام به این آدرس برود»)،
  دور زدن تحریم با دو کلیک، مسدودسازی تبلیغات با یک کلید، لاگ ساده «چه کسی چه چیزی پرسید».
- **پیشرفته:** همه زون‌ها و نوع رکوردها، DNSSEC، views، forwarderها، ACL، RRL، TSIG، انتقال زون، فهرست‌های مسدودسازی،
  آستانه‌های فشار، نگهداری لاگ، پروتکل‌ها و گواهی‌ها؛ همه در مرکز تنظیمات.
- مجوزها: `dns:read`، `dns:write`، `dns:logs` (لاگ‌ها اطلاعات حساس‌اند)، `dns:admin`.

## 9. فازبندی (هر فاز قابل استفاده و تست‌شده)

| فاز | محتوا | معیار پذیرش |
|---|---|---|
| **D0** | بستن کار «سرویس‌های من» (تست کامل، Docker، مستندات) | همه تست‌ها سبز |
| **D1 پایه** | باینری Go در همان ایمیج، container جدا، UDP/TCP، زون Primary و رکوردهای رایج، forwarder، cache، ACL ضد open-resolver، RRL، API مدیریتی، ماژول پنل + صفحه ساده زون/رکورد، راهنمای راه‌اندازی، رکورد خودکار برای دامنه‌های سرویس | تست انطباق با `dig`، ≥ ۵۰ هزار qps از cache، تست حمله amplification |
| **D2 لاگ و پایش** | ring buffer، ذخیره segment، جست‌وجو/زنده، آمار، سطوح فشار و اقدام خودکار، داغ‌ترین‌ها، اعلان | تست بار تا اشباع: سرور و پنل سالم، DNS پاسخگو برای کلاینت‌های عادی |
| **D3 دور زدن تحریم** | Smart DNS + SNI Proxy + کارت‌های آماده + چند پروکسی + Traefik passthrough | Docker pull و npm/pip از سرویس‌های تحریمی از طریق پروکسی آزمایشی |
| **D4 Resolver کامل و DNSSEC** | حل از ریشه، اعتبارسنجی DNSSEC، serve-stale، prefetch، DoT/DoH/DoQ ورودی و خروجی | مجموعه تست DNSSEC و مقایسه با Unbound |
| **D5 حرفه‌ای** | Secondary/AXFR/IXFR/NOTIFY، TSIG، Dynamic Update، امضای DNSSEC، views، فیلترینگ و RPZ، گروه‌های کلاینت، تاریخچه زون | تست تعامل با BIND/Knot به‌عنوان secondary |
| **D6 سخت‌سازی** | fuzzing، بازبینی امنیتی، تست بار طولانی، پشتیبان/بازگردانی، مستندات کامل | sign-off |

## 10. ریسک‌ها

- **تداخل با Dokploy روی 443** (فقط برای بخش تحریم): راه‌حل passthrough در Traefik یا نشانی داخلی؛ قبل از تحویل D3 روی
  Docker واقعی آزموده می‌شود.
- **ری‌استارت Docker daemon** در راه‌اندازی: کاربر زمانش را انتخاب می‌کند؛ MRK خودش انجام نمی‌دهد.
- **افزوده شدن toolchain Go به build:** فقط مرحله build چندمرحله‌ای؛ ایمیج نهایی فقط باینری را دارد.
- **حجم کار:** هر فاز جدا تحویل و تأیید می‌شود.
