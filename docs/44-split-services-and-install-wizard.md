# 44 — جدا کردن سرویس‌ها و ویزارد «افزودن سرویس»

## 1. مشکل

همه چیز در یک ایمیج و یک کانتینر بود: پنل، PGlite، Verdaccio (npm)، devpi و روتر PyPI، و موتور S3،
زیر Supervisor. سرویس‌ها از راه فایل‌های مشترک روی `/data` به هم وصل بودند و پنل آن‌ها را با
`supervisorctl` داخل همان کانتینر کنترل می‌کرد. نتیجه این بود که برای نصب باید کل بسته را با همه
پروفایل‌ها، volumeها و متغیرهایش یک‌جا می‌فهمیدید و بالا می‌آوردید.

## 2. تصمیم

- **اول فقط پنل.** ایمیج `mrk-panel` فقط پنل و پایگاه‌داده داخلی‌اش را دارد و بدون هیچ پیش‌نیازی بالا می‌آید.
- **هر سرویس یک ایمیج و یک Compose جدا** (`ghcr.io/<owner>/mrk-<service>:<version>`). نسخه سرویس‌ها
  همیشه با نسخه پنل یکی است: پنل نسخه خودش را در `MRK_IMAGE_TAG` دارد.
- **ویزارد داخل پنل** («سرویس‌های من ← افزودن سرویس»). برای هر سرویس:
  1. روش اجرا: Dokploy، Coolify یا Docker Compose روی سرور یا نصب خودکار: پنل خودش با API ‏Dokploy یا Coolify می‌سازد و deploy می‌کند؛
  2. چند مقدار لازم، با پیش‌فرض درست؛
  3. یک `compose.yaml` و یک `.env` آماده، با قدم‌های همان ابزار. `.env` کلید اتصال یک‌بارمصرف را دارد؛
  4. «اتصال و امتحان»: پنل با همان کلید وصل می‌شود و جواب دادن سرویس را بررسی می‌کند.
- ایمیج یکپارچه قدیمی (`deploy/appliance`) حذف شد؛ همه سرویس‌ها image خودشان را دارند.
  هنوز نصبی از آن وجود ندارد، پس ابزار مهاجرت لازم نیست.

## 3. اجزای مشترک بین Stackها

Stack پنل که همیشه اول نصب می‌شود این‌ها را با **نام ثابت** می‌سازد و Stackهای سرویس فقط به آن‌ها
وصل می‌شوند (`external: true`):

| نام | نوع | کاربرد |
|---|---|---|
| `mrk-net` | شبکه `internal` (بدون اینترنت) | پنل سرویس‌های HTTP را با نامشان صدا می‌زند، مثلاً `http://mrk-agent:7070` |
| `mrk-dns-run` | volume | سوکت و توکن مدیریت موتور DNS |
| `mrk-firewall-run` | volume | سوکت دستیار فایروال |

برای همین سرویس‌هایی که سوکت یا دسترسی میزبان دارند (Agent، DNS، فایروال) باید روی **همان سرور** پنل
اجرا شوند؛ ویزارد این را روی کارت هر سرویس می‌گوید.

**پنل بومی (بدون Docker).** `scripts/install-native.sh` فقط پنل را با systemd نصب می‌کند و
`MRK_PANEL_RUNTIME=native` می‌گذارد. پنل بومی روی `mrk-net` نیست، پس ویزارد همان Stackها را با این تفاوت
می‌دهد: Agent پورت `127.0.0.1:7070` و S3 پورت مدیریت `127.0.0.1:9001` را فقط روی loopback منتشر می‌کنند و
DNS و فایروال به‌جای volume مشترک، پوشه‌های `/run/mrk-dns` و `/run/mrk-firewall` سرور را mount می‌کنند.

## 4. کلید اتصال

قبلاً Agent و فایروال در اولین اجرا کلید را خودشان می‌ساختند و در گزارش چاپ می‌کردند و کاربر باید آن را
پیدا و در پنل وارد می‌کرد. حالا:

- پنل کلید ۳۲ بایتی را می‌سازد، فقط در SecretStore رمزشده نگه می‌دارد و یک بار در `.env` نشان می‌دهد؛
- سرویس آن را از `MRK_AGENT_PAIRING_KEY` / `MRK_FIREWALL_PAIRING_KEY` می‌خواند و در فایل کلیدش
  (حالت 0600) می‌نویسد. کلیدِ env همیشه برنده است، پس اگر در ویزارد کلید تازه بسازید و دوباره deploy کنید،
  کلید نو اعمال می‌شود؛
- ساختن دوباره فایل‌ها کلید در انتظار قبلی را جایگزین می‌کند.

DNS کلید ندارد: موتور توکن مدیریت را خودش در `mrk-dns-run` می‌نویسد و پنل آن را می‌خواند.

S3 از توکن مدیریتی استفاده می‌کند که پنل از قبل دارد (`<data>/modules/s3/admin.token`)؛ ویزارد همان را
در `MRK_S3_ADMIN_TOKEN` می‌گذارد، پس ساختن دوباره فایل‌ها موتورِ در حال کار را از کار نمی‌اندازد.

## 4.1. S3 جدا

| قبلاً (یکپارچه) | حالا (`mrk-s3`) |
|---|---|
| پنل `config.json` را روی `/data` مشترک می‌نوشت و موتور با mtime آن را می‌خواند | پنل همان snapshot را با `PUT /admin/config` روی `mrk-net` به موتور می‌فرستد؛ موتور آن را اعتبارسنجی و در volume خودش (حالت 0600) ذخیره می‌کند |
| موتور رمز کلیدها را از SecretStore پنل می‌خواند | رمز هر کلید همراه snapshot فرستاده می‌شود (فقط روی API مدیریتی احراز‌شده) |
| مدیریت فقط روی `127.0.0.1:9001` | `0.0.0.0:9001` داخل کانتینر، فقط روی شبکه‌های همان Stack (پورتی منتشر نمی‌شود) |
| نشانی ثابت `127.0.0.1:9000` | پنل نشانی‌ها را در `control-plane/s3-engine.json` نگه می‌دارد (پیش‌فرض `http://mrk-s3:9000` و `:9001`)؛ مدیر فایل، پشتیبان‌ها و «فضای من» همه از همان می‌خوانند |

اگر موتور در دسترس نباشد یا با volume خالی دوباره شروع شود، پنل هر ۳۰ ثانیه بررسی می‌کند و snapshot را
دوباره می‌فرستد (`/admin/health` → `config_loaded`). داده سطل‌ها فقط در volume خود `mrk-s3` است.

## 5. API

| مسیر | اجازه | کار |
|---|---|---|
| `GET /api/v1/install/catalog` | `services:read` | فهرست سرویس‌ها، آمادگی (`ready`/`planned`)، ایمیج، تنظیمات، وضعیت اتصال |
| `POST /api/v1/install/{id}/bundle` | `services:operate` + اجازه نوشتن همان سرویس | `compose.yaml` و `.env` (با کلید تازه) |
| `POST /api/v1/install/{id}/connect` | همان | ذخیره اتصال با کلید در انتظار و امتحان آن |

اجازه نوشتن هر سرویس همان اجازه‌ای است که صفحه خودش برای اتصال می‌خواهد: `agent:write`،
`firewall:write`، `dns:write`. اگر اتصال با متغیرهای محیطی (`MRK_AGENT_URL`…) تنظیم شده باشد،
ویزارد آن را عوض نمی‌کند (409 `managed_by_environment`).

قالب‌های Compose در `apps/control-plane/src/mrk_control_plane/modules/install_catalog.py` هستند؛
ویزارد همان متن را بی‌تغییر می‌دهد و تست‌ها (`tests/test_install_wizard.py`) بررسی می‌کنند که هر قالب
Compose معتبر، فقط‌خواندنی، بدون capability اضافه و بدون پورت عمومی باشد.

## 6. ایمیج‌ها

`deploy/images/Dockerfile`، یک target برای هر ایمیج:

| target | محتوا | کاربر |
|---|---|---|
| `panel` | پنل، رابط کاربری، روتر PyPI (دیتابیس: سرویس `mrk-db` با PostgreSQL 17) | 10001 |
| `agent` | `mrk-agent` | root با `DAC_READ_SEARCH`+`DAC_OVERRIDE` (مثل قبل) |
| `firewall` | `mrk-firewall` + `nft` | root فقط با `NET_ADMIN` |
| `dns` | باینری Go موتور DNS | از uid 0 شروع و فوراً به 10001 |
| `s3` | `mrk-s3-engine` | 10001، بدون capability |

CI (`split-images`) هر چهار را می‌سازد و بالا آمدن پنل به تنهایی را امتحان می‌کند. انتشار
(`publish-split`) هر کدام را جدا با SBOM، provenance، اسکن Trivy و امضای attestation منتشر می‌کند.
