# طرح یکپارچه‌سازی مدیریت فایروال

## هدف

پنل MrK DevAssist باید تنها محل مدیریت این دو بخش مستقل باشد:

1. **سیاست ورودی و پورت‌ها:** باز یا بسته بودن پورت‌های میزبان و پورت‌های منتشرشده Docker؛
2. **دفاع پویا:** مسدودسازی IPهای مهاجم، allowlist و banهای موقت یا دائمی.

این طرح جایگزین تدریجی تنظیم هم‌زمان UFW، اسکریپت دستی `PAASIFY-DOCKER-FW` و بخش فایروال پنل می‌شود. تا پایان مهاجرت، قوانین موجود حذف نمی‌شوند.

## مرزبندی مسئولیت‌ها

- Helper فقط table اختصاصی `inet mrk` را مدیریت می‌کند و chainهای Docker/Dokploy را تغییر نمی‌دهد.
- برای ترافیک سرویس‌های خود میزبان chain ورودی و برای پورت‌های publishشده کانتینرها chain forward وجود دارد.
- blocklist پیش از قوانین allow ارزیابی می‌شود، ولی allowlist مدیریتی و اتصال‌های established/related باید از قفل شدن مدیر جلوگیری کنند.
- هر تغییر به‌شکل atomic اعمال می‌شود؛ ruleset ناقص نباید جایگزین ruleset فعال شود.

ساختار پیشنهادی:

| بخش | وظیفه |
|---|---|
| `mrk_input` | پورت‌های سرویس‌های مستقیم میزبان |
| `mrk_forward` | پورت‌های منتشرشده Docker/Swarm |
| `mrk_prerouting` یا setهای مشترک | blocklist و allowlist آدرس‌ها |
| setهای timeoutدار | ban موقت بدون بازنویسی کل ruleset |

## مدل قانون پورت در پنل

هر قانون حداقل این فیلدها را دارد:

- نام و توضیح؛
- پروتکل: TCP، UDP یا هر دو؛
- یک پورت، چند پورت یا بازه پورت؛
- مبدأ: عمومی، CIDR مشخص یا allowlist نام‌دار؛
- دامنه اعمال: `host`، `docker` یا `both`؛
- وضعیت فعال/غیرفعال و ترتیب/اولویت؛
- ثبت لاگ با rate limit اختیاری.

نمونه سیاست فعلی سرور:

- عمومی TCP: `25,53,80,110,143,443,465,587,993,995,4190,5000,14000-14999`
- عمومی UDP: `53,443,14000-14999`
- شبکه مدیریت `85.185.239.152/29` روی TCP: `6022,3000,8080,9000-9001`
- سایر اتصال‌های ورودی جدید: رد یا drop با لاگ rate-limited.

این فهرست فقط نقطه شروع مهاجرت است و پیش از enforce باید با سرویس‌های واقعی همان سرور تطبیق داده شود.

## الزامات جلوگیری از قطع دسترسی

- حالت پیش‌فرض Helper همچنان `dry-run` باشد.
- صفحه preview باید diff دقیق ruleset فعلی و بعدی را نشان دهد.
- فعال‌سازی enforce به تأیید صریح مدیر نیاز داشته باشد.
- پیش از اعمال، قانون SSH/مدیریت و CIDR مدیر اجباری باشد.
- IP درخواست‌کننده به‌طور موقت allow شود، مگر مدیر آگاهانه آن را غیرفعال کند.
- ruleset با `nft --check` اعتبارسنجی و سپس atomic load شود.
- نسخه last-known-good ذخیره شود.
- پس از تغییر پرخطر، تایمر rollback خودکار فعال شود و مدیر فقط پس از تست آن را تأیید کند.
- دستور بازیابی اضطراری خارج از پنل و قابل اجرا از کنسول سرور ارائه شود.
- IPv4 و IPv6 هم‌زمان پوشش داده شوند.
- پورت‌های Docker Swarm/Dokploy، DNS و مسیر مدیریت پنل محافظت ویژه داشته باشند.

## مراحل مهاجرت

1. قوانین UFW و اسکریپت `PAASIFY-DOCKER-FW` فقط خوانده و در پنل import شوند.
2. قوانین معادل در حالت dry-run تولید و با وضعیت واقعی مقایسه شوند.
3. SSH، پنل، HTTP/HTTPS، DNS، ایمیل، Registry و پورت‌های دیتابیس از داخل و خارج آزمایش شوند.
4. ruleset جدید با rollback زمان‌دار enforce شود.
5. بعد از تأیید دسترسی، jump قدیمی موقتاً حذف شود:

   ```bash
   sudo iptables -D DOCKER-USER -j PAASIFY-DOCKER-FW
   ```

6. اگر مشکلی رخ داد، jump فوراً برگردد:

   ```bash
   sudo iptables -I DOCKER-USER 1 -j PAASIFY-DOCKER-FW
   ```

7. فقط پس از چند دور تست و reboot آزمایشی، UFW و فایل/سرویس قدیمی بازنشسته شوند.

## وضعیت فعلی تا قبل از پیاده‌سازی این طرح

در نسخه فعلی `mrk-firewall` فقط block/allow آدرس‌های IP را در table خودش مدیریت می‌کند و مدیریت عمومی باز و بسته کردن پورت‌ها را بر عهده ندارد. بنابراین تا زمان تکمیل مهاجرت، برای یک پورت Docker-published باید هر سه مورد هماهنگ باشند:

1. انتشار پورت در Compose؛
2. سیاست UFW موردنظر؛
3. allow همان پورت در اسکریپت `PAASIFY-DOCKER-FW`، پیش از قانون DROP نهایی.

این محدودیت باید در رابط فعلی پنل نیز شفاف نمایش داده شود تا کاربر تصور نکند allowlist فایروال به‌تنهایی یک پورت را باز می‌کند.
